# RIM·CS — памятка для Claude

Бесплатное Telegram Mini App для подготовки комментатора (русский) к матчам CS2 тир-1/тир-2.
Всё должно оставаться бесплатным.

## Правила работы (от владельца)
- Что попросили сделать — сразу в main и на сайт, без отдельных веток.
- Если владелец только спрашивает — отвечать, ничего не менять и не запускать.
- Проверочные (probe) workflow, которые только читают источники, — можно; после — удалить.
- Ключи (PANDASCORE_TOKEN, GIGACHAT_KEY, GEMINI_KEY) только в GitHub Secrets, в чат не просить.
- Не обходить защиту сайтов (HLTV и др.). HLTV: не чаще 1 запроса / 2.5 с, только в полном сборе. Единичный 403 на любой странице — пауза только для неё (`hfail:`, 1/3/7 дней), три 403 подряд — стоп до следующего запуска; 429/503 — ждём минуту и один повтор, повторно — стоп. Игроки идут очередью `hltv_players_warm` (нет данных → старая версия → давно не обновлялись; ближайшие матчи вперёд), до `MVP_PER_RUN`=80 за сбор.
- Отвечать по-русски, коротко, без технических подробностей, если не спросили.
- Когда диалог становится длинным и расходует много лимита (много больших правок, длинные логи,
  десятки шагов) — обновить этот файл: что сделано, текущее состояние, открытые задачи, новые
  правила владельца. Закоммитить в main с `[skip ci]` и сказать владельцу одной строкой, что
  памятка обновлена и можно начать новый диалог («Обратись к CLAUDE.md, проект RIM·CS»).
  Файл держать коротким: заменять устаревшее, а не дописывать историю.

## Устройство
- Версия сайта: при публикации (pages.yml и collect.yml) `tools/stamp.sh` берёт свежие файлы приложения из main, пишет sha в `BUILD` и `docs/version.txt`; приложение сверяет (`checkVersion`) и само перезагружается на `?v=…` — против кэша Telegram.
- `docs/index.html` — всё приложение (SPA, один файл). Данные читает из ветки `data`
  через raw.githubusercontent.com (`dfetch`), запасной вариант — `docs/data` в Pages.
- `collector/collect.py` — сборщик. Режимы: полный (HLTV, Liquipedia, нейросеть), `STATS_ONLY=1`, `NEWS_ONLY=1`.
- `collector/save_data.py` — слияние и запись в ветку `data` (orphan, один коммит, force-with-lease).
- Workflow: `collect.yml` (полный, каждые 3 ч, лимит 90 мин, публикует Pages), `stats.yml` (~40 мин), `news.yml` (5 мин), `pages.yml` (при изменении docs/).
  GitHub запускает расписание с опозданием → в воркере есть `scheduled()`: по крону Cloudflare раз в 5 мин запускает news.yml, раз в 30 — stats.yml (нужны секрет GH_TOKEN и Cron Trigger в Cloudflare — делает владелец).
- Live: Cloudflare Worker `https://rimcs-live.vladrimskij.workers.dev` → api.bo3.gg (/matches, /games, /games/ID/players_stats), код в `tools/cloudflare-worker.js`; владелец вставляет его сам в редакторе Cloudflare.
- Нейросеть: Gemini `gemini-flash-latest` (основная; при 503 ждёт и переходит на `gemini-flash-lite-latest`,
  она не принимает thinkingConfig; 2.5-flash-lite снята), GigaChat (запасная). Ключ GEMINI_KEY добавлен 04.11.
- id игроков HLTV: со страницы рейтинга (`rkpl`, тот же запрос), составов событий и старого кэша страниц команд (`tpl:`). У dust2.us страниц игроков нет (проверено). Порядок в полном сборе: рейтинг → очередь игроков → карточки. 05.11 HLTV стабильно отказывает на /team/ и /results?team= части команд — эти страницы уходят на паузу.
- Тир-2 (tier «a» у PandaScore/bo3): турнир показываем, только если ≥50% участников из топ-25 рейтинга Valve
  (`tier2_ok`, `TIER1_TOP`, `TIER2_SHARE`). StarLadder, Thunderpick, FISSURE на bo3 — уже тир «s».
- Вето прошедших серий: матчи последнего месяца — из ленты dust2.us /results (одна страница, ~350 матчей, фильтры dust2 игнорирует), старше месяца не ищем (решение владельца); найденное вето при пересборке сохраняется (prev_veto); дата — из ленты (`data-date`); dust2 работает и в быстром сборе; само вето с dust2.us;
  dust2: раз в 1 с, без лимита за сбор (`VETO_NEW_LIMIT`=1500); отказов от dust2 не было. У bo3.gg вето нет.
- Страница прошедшего матча (`.ovl.sov`) листается целиком, шапка уезжает; карты — горизонтальный трек.
- Статистика матча: первым блок «На кону» (`stakeBlock`/`stakeRows`: сетка из results + призовые и путёвки
  `spots` с HLTV). Шпаргалки больше нет (убрана по просьбе владельца).
- Квадраты карт: картинки `docs/img/maps/*.webp` (Valve, 480px, из ghostcap-gaming/cs2-map-images), `mapBg()`;
  карт вне набора (Cache) — градиент. Бан красный, пик зелёный.
- Логотипы: `data/logos.json` (`build_logos`): bo3.gg (цветные) → PandaScore (кроме lightmode) → HLTV;
  недостающие ищутся на bo3 по названию. В вебе `PRIMARY` важнее остальных.
- Фон карточек турниров: `tr["bg"]` = баннер bo3, иначе обложка (`bo3_tour_bg`).
- Ручные русские имена: `NAME_RU` в collect.py (PR → Олдрич Новый, xelex, xertioN, sycrone) — важнее нейросети.
- Матч с одной командой: карточка тоже есть (`tbd`, `tbd_side`), соперник — `opp` {kind winner/loser, cands} из плашки dust2 «PARIVISION/NaVi winner» (`tbd_opp`, `team_names_index`); на сайте `withOpp` вставляет команду-заглушку со смешанным логотипом (`mixLogo`), «Статистика» заполнена по известной команде (На кону, VRS «сейчас», карты и стороны, последние игры, форма), у соперника во всех цифрах нули (0%, 0/0, 0–0); вероятный пик и личные встречи — «Ждём соперника». На главной под названием видна версия сайта (v…).
- Карточки матчей — для всех матчей недели с двумя командами; дальше 3 дней «лёгкие» (без фактов нейросети, новости один раз).
- Страницы команд: состав с Liquipedia (до 40 новых команд за сбор), иначе строки из игроков bo3; id игроков HLTV
  со страницы команды (кэш `tpl:`), MVP/мажоры `hltv_player_info` (кэш `pinfo5`, `PINFO_TTL_DAYS`=21; очередь перечитывает игрока раньше, только если его команда доиграла турнир после прошлой проверки — `event_ended_since`).
  `team_by_name` пробует алиасы и «X Team» (BETBOOM → BetBoom Team).
- Вкладка матча «Команда»: две страницы `team:pos` / `team:players` (Позиции слева, при открытии матча — Игроки) в общем треке свайпа (как фильтры новостей: строка подвкладок `.tfilt` в шапке, `hasSub`, `subGroup`), карты в «Позициях» липкие (`.poswrap > .mapsel`) и листаются свайпом как зона карты (`zctx`: общий свайп для `data-map` и `data-pmap`, на крайней карте — дальше по вкладкам). Позиции — `data/positions.json` из ProRoles (proroles.gamesenselab.pro, открытый `/pp/index.json`, `build_positions`, раз в 20 ч): роль CT/T (`roleRu`, Anchor → «Опорник») и зона с % (`CALL_RU`: коллауты по-русски, как в эфире — шорт, лонг, мейн). Команда сопоставляется по никам (`posTeam`). Только топ-50 команд, 7 карт.
- Строка игрока: статус в составе плашкой (Замена + «заменяет X», Аренда + «в аренде из X», На просмотре, Неактивен). Кого заменяет — шаблон Liquipedia `{{Stand-in|id|for=}}`, иначе неактивный с той же датой, иначе единственный неактивный (`stand_for`); владелец аренды — `team=`, иначе вторая «Present»-запись в истории игрока (`loan_owner`). Составы с заменой/арендой/просмотром перепроверяются раз в сутки — так ловится переход в основу или конец аренды — одинаково в матче и на странице команды; во вкладке «Игроки» матча статистики нет (убрана 05.11); на странице команды — `statRow` «📊 3 мес.» (K/D, ADR, KAST). Мажоры `majLine` (🏆 — чемпион, иначе место).
- «На кону» и призовые: всего → клубу → команде. Регионы по-русски, «Мир» с большой буквы, VRS-группы участников с плашкой. Пояснения под VRS-прогнозом нет. Карты — за 3 мес. (`MAPS_WINDOW_DAYS`=90).
- Флаги: `CC_FIX` (UK→GB). Русские имена — `add_pronunciation` через GigaChat Max напрямую (Gemini — запасной путь), Max без дневной планки (решение владельца 05.11), до 100 команд за полный сбор; кэш навсегда. Трофеи: места 1–4 этого года — сначала по сеткам bo3.gg (`bo3_prize_places`/`bo3_tour_places`: финал → 1/2, матч за 3-е → 3, иначе проигравшие финалистам в предыдущем матче → 3 или 3–4; тир s/a; кэш `bo3_places.json`, доигранные навсегда), плюс места с HLTV, которых у bo3 нет. Liquipedia для трофеев не подошла: страницы результатов собираются шаблоном, только через тяжёлый parse.
- Карты сыгранных серий: `sides` — раунды за CT/T по командам (`map_sides`, из раундов bo3; у старых итогов дописываются из кэша). Показываются внутри матча и в личных встречах (h2h maps тоже несут `sides`), не в списке «Завершённые».
- Новости (лента и матчи): разные посты НЕ объединяются (`dedupe_strict`): склеиваются только повторы одной новости — почти тот же текст (≥75% общих слов, ±48 ч) или та же картинка (`ph`: отпечаток dHash через Pillow, разница ≤6 бит, ±12 ч, ≥3 общих слова; считается раз на пост за 48 ч, хранится в tg_cache); главной — самая подробная; фото и текст всегда от одного поста. Текст поста — целиком (без обрезки). У поста-ответа цитату (`js-message_reply_text`) не берём — только собственный текст.
- Новости с большим видео из Telegram (`video: "tg"`) не отсеиваются: на сайте обложка и кнопка «Смотреть видео в Telegram» (в нашем плеере такие не играют — веб-версия Telegram не отдаёт файл).
- Факты для эфира: сначала из новостей, все кликабельны (без новости — открываются как заметка «статистика»).
- Год у турниров на сайте — `withYear()`.
- Скорость: `dfetch` — кэш в памяти и localStorage (`dc:`), отдаёт сразу, свежее подкачивает в фоне (старше 20 с); `dfetch(u, true)` и `state.refreshing` — только сеть. `prefetchAll` в простое подкачивает рейтинг, ленту, сетки идущих турниров и 6 ближайших матчей. Переходы: `body.nav` на 360 мс → анимация `viewIn` (transform/opacity), окна `popIn`.
- Иконка веб-приложения: микрофон с красной лампой «в эфире» и подписью CS (`docs/img/icon/icon.svg` → png 512/192/180), `docs/manifest.webmanifest`, apple-touch-icon. На главной название RIM·CS стоит над первой плиткой (34px), всё по центру экрана.
- Сыгранный турнир: вкладки «Обзор» (сетка, призовые, участники; сетка у старых итогов достраивается один раз) и «Матчи» (сыгранные серии).
- Турниры: две вкладки — «Актуальные» (идут сейчас сверху, ниже грядущие по месяцам, обычным списком сверху вниз, без центрирования) и «Завершённые».
- Свёрнутый версус: регионы коротко по-английски (`REG_MINI`: EU/AM/AS); остальное — по-русски.
- Участники турнира: плитки по 4 (`participantsBlock`: логотип, название, как попали через `howRu` — «VRS Северная Америка», «Закрытая квалификация Азии», «Стадия 2»); у мажора добираются все команды по стадиям приглашений.
- Призовые и участники с HLTV (`tournament_extras`): идущие и ближайшие 2 мес.; когда турнир доигран, его данные остаются навсегда (кэш `event3:`). Прошлые турниры (сыгранные до 05.11) не дособираем — решение владельца; архив HLTV не читаем. До 8 новых страниц событий за сбор. Поиск события мягкий (по доле слов при совпадении года).
- Окна (MVP, мажоры, трофеи): зона нажатия — круг вокруг значка (`.medal[data-pop]::after`, ≥48px), «Мейджоры» — видимая плашка-кнопка с зоной на 8px вокруг; закрываются прокруткой (не в первые 600 мс, не от сдвига < 24 px) и тапом по свободному месту.
- Стрелок разделов (`.snav`) в «Статистике» больше нет (убраны по просьбе владельца 05.11).
- `save_json` пишет непривычные объекты текстом (`default=str`), чтобы сбор не падал.
- Названия команд (шапка матча, версус сыгранной серии, состав, стадии мажора, участники) ведут на страницу команды (`data-tname`).
- Обзор турнира: каждая стадия во всю ширину экрана, без прокрутки вбок (столбцы делят ширину; в сетке с 3+ столбцами — короткие названия `shortName`), стадии листаются вверх-вниз с притягиванием (`scroll-snap` proximity). Порядок стадий: доигранный — плей-офф сверху; идущий — плей-офф наверх, если идёт или до начала < 12 ч, иначе текущие (группа A, потом B) → будущие → сыгранные.
- Швейцарка (`isSwiss`: формат swiss или раунды без сетки/«default» по 6+ матчей, в т.ч. стадии мажора с одним «Раунд 1») — `swissHtml` «по счёту», как на HLTV/bo3: столбец — раунд, матчи сгруппированы по счёту (`.swgr[data-rec]`), победитель в зелёном кольце, проигравший бледный, плашки белые на сером; сверху столбца зелёная плашка вышедших (3:0, в последнем — 3:1 и 3:2), снизу красная вылетевших; стрелки `drawSwiss` (зелёная — победитель в w+1, красная — проигравший в l+1).
- Сетка: матч за 3-е место (у bo3 бывает отдельной стадией) — в плей-офф под гранд-финалом, без линий.
- Статистика матча: порядок — На кону, VRS, пик, карты, зона карты (последние игры на карте), личные встречи, форма (свёрнута до 3, `data-formall`).
- Личные встречи: квадраты без раундов, матч нажимается (`sid` → `series`, `_h2h_matches`).
- Строка «Турнир» у игрока: зелёным/красным, если сильно лучше/хуже 3 мес. (`vsBase`: K/D ±15%, ADR ±12%, KAST ±6).
- Мажоры нажимаются всегда (нет списка — подсказка); у тренеров тоже мажоры/MVP. Окна закрываются движением пальца (события scroll не слушаем) и тапом по свободному месту (touchend без сдвига, не раньше 250 мс после открытия).
- Страница команды: «Будущие игры» до 10 (`bo3_upcoming`). На каждом сборе сверяется с карточкой матча этой команды: состав (если у страницы он не с Liquipedia — берётся из матча), трофеи, MVP/мажоры; плюс MVP/мажоры из кэша HLTV без запросов. Без Liquipedia в состав попадают только игравшие последние карты (запасные не показываются).
- Статистика: `DETAILS_NEW_LIMIT`=3500 в полном / 1500 в быстром, `GAMES_NEW_LIMIT`=2000 (bo3 не блокирует), stats.yml лимит 45 мин; bo3 ищет команду и без «Esports/Gaming/…» (FUT Esports). У новичков команды цифр нет, пока не сыграют за неё карт.

- Прогноз вето (`build_prediction.choose`): бан = частота банов (вес свежести, полураспад 60 дн., `br`) + первый бан (`fr`) − 2×(моя сила на карте − сила соперника); пик = частота пиков (`pr`) + 2×разница сил + 0.1×пики против этого соперника (`vs`). Сила на карте — винрейт со сжатием (+1.5/+3). Кто начинает вето: team2 из пары bo3 (`_bo3_starter`), а в именных группах (Group A/B… — GSL у IEM, ESL, FISSURE) — команда ниже в VRS (сильный посев уступает первый бан). На 357 сериях BO3: начинающий угадан 72% → 79%; с этим правилом пики по командам ~35%, первый бан ~69%, десайдер ~33%, сыгранные карты ~65% (если знать начинающего точно — пики 41,5%, первый бан 82%). `tools/veto_backtest.py` подставляет настоящего начинающего — это потолок, а не то, что на сайте. Правил вето на страницах турниров Liquipedia нет (проверено 05.11), только посев. Карточки «Вероятного пика»: номер, кто пикает, карта и счёт серии; строки с процентами нет (решение владельца 05.11). Шанс победы в серии — в шапке матча («Победа N%», `winPct`, не в свёрнутой). Без коэффициентов вероятность — от разницы очков VRS (шкала 400; 74% угаданных победителей, Брайер 0.18), карты сдвигают её чуть-чуть: винрейты карт почти не лучше монетки.

## Источники
- PandaScore: расписание, турниры. bo3.gg: матчи, карты, статистика игроков, сетки, коэффициенты (`bet_updates` — линия Thunderpick, наценка ~7%; Pinnacle точнее, но открытого API нет — через агрегатор OddsPapi с ключом, не подключали). Журнал прогнозов `data/odds_log.json` (`odds_log_put` — последняя линия до начала, `odds_log_resolve` — итог с bo3 через 5 ч, сводка: % побед фаворита, Брайер, по корзинам вероятности). Вероятности из коэффициентов — степенным методом (`devig`, подтягивает фаворита ближе к точной линии); подписи про букмекера на сайте нет (решение владельца).
- HLTV (решение владельца 06.11 — только то, чему нет надёжной замены): рейтинг VRS (1 запрос), /events и страницы событий (путёвки, призовые, участники; доигранные — навсегда), инвайты мажора, страницы игроков (MVP и мажоры). Страницы команд (/team/) и /results?team= больше НЕ запрашиваем: трофеи — сетки bo3 (+ старые достижения HLTV из кэша `ach:`), сводка вето — свой архив dust2 (`team_veto_matches`: лента за месяц + сохранённые вето `match:*` за 3 мес., работает и в быстром сборе), id игроков — со страницы рейтинга (`rkpl`) и составов событий. Проверено 06.11: на Liquipedia есть призовые по местам (без команд), участники с отбором, мажоры с местами; путёвок и MVP (кроме ссылок «X earns MVP at …» в итогах) там нет, VRS — только на лету.
